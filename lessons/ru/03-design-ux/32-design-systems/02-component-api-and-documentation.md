## Что это такое

API компонента — это интерфейс, который компонент предлагает своим потребителям: какие входные данные он принимает, какие варианты допускает, что рисует в каждом состоянии и от чего намеренно отказывается. Документация — это короткая страница, которая утверждает эти свойства, показывает каждый вариант и фиксирует решения за ними.

## Почему это важно

Компонент со слишком большим числом опций — это компонент, которым никто не сможет пользоваться согласованно: дайте кнопке двенадцать свойств, и каждая команда передаст свою комбинацию, а согласованность, ради которой строили систему, исчезнет. Компонент со слишком малым числом опций форкают на первом же исключении, и он навсегда уходит из системы. Документация — то, что останавливает второй провал, потому что говорит потребителю, что делать вместо форка.

## Ключевые идеи

### Проектируйте API от применений, а не от реализации

Сначала соберите реальные места вызова и спроектируйте наименьший интерфейс, который их покрывает. Свойство, о котором никто не просил, — спекулятивно, и им будут пользоваться непоследовательно.

```text
Применения в продукте:
  основное действие на странице      "primary"
  второстепенное действие рядом      "secondary"
  разрушительное действие            "danger"
  ссылка в стиле кнопки              вариант "link"
-> variant: primary | secondary | danger | link
-> всё остальное (размер, иконка) отдельно и с именами
```

### Предпочитайте небольшой набор именованных вариантов множеству независимых свойств

Независимые булевы значения складываются в состояния, которых никто не рисовал: `large` и `ghost` и `loading` и `icon-only` — это не одна из четырёх кнопок, которые кто-либо нарисовал. Именованные варианты держат набор конечным и обозримым.

### Каждый компонент документирует состояния, а не только состояние по умолчанию

Загрузка, отключён, ошибка, пусто и длинный контент. Потребитель, который не видит состояние, вынужден его придумать — и придумает иначе, чем следующая команда.

### Напишите «делайте» и «не делайте» для каждого компонента

По две-три строки. «Используйте опасную кнопку для действия, которое нельзя отменить. Не используйте её для важного основного действия». Это тот текст, который предотвращает форк.

### Документируйте решение, а не только результат

Запишите, почему набор вариантов именно такой и что отвергли. Следующий, кто предложит пятый вариант, увидит аргумент вместо того, чтобы повторить его.

## Практика

### Спроектируйте API одного компонента

Возьмите самый дублируемый паттерн, соберите пять реальных мест вызова, напишите API с его вариантами и состояниями, затем реализуйте его и перенесите места вызова.

Готово, когда: все пять мест вызова используют компонент без локальных переопределений, а в API нет опции, которой не пользуется ни одно из них.

### Полностью задокументируйте один компонент

Напишите его страницу: назначение, варианты, каждое состояние, «делайте» и «не делайте» и одно зафиксированное решение.

Готово, когда: человек, никогда не пользовавшийся компонентом, может собрать корректный экран по одной странице, не читая его исходный код.

## Частые ошибки

- **Свойство на каждую возможность** — комбинации становятся непредсказуемыми, а визуальный результат расходится; исправить: назовите небольшой набор вариантов и откажите остальным.
- **Форк на первом исключении** — исключение уходит в продукт вне системы, и форк накапливается; исправить: опишите «делайте» и «не делайте» и предложите поддерживаемую альтернативу.
- **Документация только с состоянием по умолчанию** — потребители придумывают состояния загрузки и ошибки по-разному; исправить: покажите каждое состояние на странице.
- **Фиксация результата без решения** — одно и то же предложение пересматривают каждый квартал; исправить: запишите, что отвергли и почему.
- **Миграция существующих мест вызова не сделана** — система выходит рядом со старым кодом, и оба остаются; исправить: переносите места вызова как часть определения готовности компонента.
