## Что это такое

Аутентификация устанавливает, кто вызывает систему. В современном API вызывающий обычно предъявляет токен, выданный провайдером идентификации, а не пароль, и OAuth2 описывает, как этот токен получают: кто просит доступ, кто аутентифицирует пользователя, как клиент доказывает собственную личность и что позволяет выданное разрешение. Потоки различаются по виду клиента, который просит доступ, и по тому, присутствует ли при этом пользователь.

## Почему это важно

Неверно выбранный поток — это то, как система в итоге привозит секрет внутрь мобильного приложения или просит пользователя ввести свой пароль прямо в чужой сервис. Каждый поток существует потому, что определённый вид клиента не может хранить секрет или не может перенаправлять браузер. Понимание, зачем они существуют, делает правильный выбор очевидным, а небезопасные сокращения — узнаваемыми как сокращения, а не как настройки.

## Ключевые идеи

### Стороны различны, и их секреты тоже

Владелец ресурса — это пользователь; клиент — приложение, которое просит доступ; сервер авторизации выдаёт токены; сервер ресурсов их принимает. Ключевой вопрос для любого потока — кто из них может хранить секрет. Серверное приложение может; страница в браузере и мобильное приложение не могут, и именно это и закодировано в выборе потока.

```text
пользователь -> клиент -> сервер авторизации -> токен -> сервер ресурсов
```

### Authorization code с перенаправлением — вариант по умолчанию для клиентов с пользователем

Пользователя отправляют на сервер авторизации, он аутентифицируется там и возвращается к клиенту с короткоживущим кодом, который клиент обменивает на токены. Пароль пользователя клиент не видит никогда, а сам код бесполезен без собственных учётных данных клиента. Эта форма работает для серверных приложений, а с дополнительным шагом доказательства — и для клиентов, которые не могут хранить секрет.

### Поток client credentials — для сервисов без пользователя

Когда один бэкенд вызывает другой и пользователя в этом нет, вызывающий сервис аутентифицируется как он сам и получает токен для своей личности. Здесь нет ни шага согласия, ни пользователя, что сильно упрощает поток, — и он уместен только там, где вызывающий действительно действует от своего имени, а не от чьего-то другого.

### Секрет нельзя хранить в браузере или в мобильном бинарнике

Всё, что попало на устройство пользователя, можно прочитать. Такой клиент поэтому приходится считать публичным, и любой поток, требующий от него хранить секрет, сломан по построению. В этом причина дополнительного шага доказательства и причина, по которой поток в стиле implicit grant, возвращающий токен прямо в браузер, был вытеснен.

### Токены должны быть краткоживущими, а обновление — отдельным разрешением

Access token предъявляется при каждом запросе и чаще всего становится добычей копирования, поэтому он должен быстро истекать. Refresh token, который хранят тщательнее и используют только против сервера авторизации, получает новый access token без нового взаимодействия с пользователем. Долгоживущие access token убирают запас прочности, благодаря которому утечку ещё можно пережить.

### Области доступа выражают разрешение, а не роль пользователя

Область доступа говорит, что клиент попросил разрешения делать, — читать заказы, писать платежи, — и на что пользователь дал согласие. Это не утверждение о полномочиях пользователя внутри приложения. Разделение этих двух вещей и позволяет сделать разрешение узким, не ограничивая того, что пользователь может делать в другом контексте.

## Практика

### Выберите поток для трёх клиентов

Для серверного веб-приложения, одностраничного приложения и ночной пакетной задачи укажите, какой поток использует каждое и где хранится его секрет.

Готово, когда: каждый выбор называет сторону, которая хранит секрет, и ни один клиент, который не может его хранить, не обязан это делать.

### Проследите жизненный цикл токена

Опишите последовательность от первого запроса пользователя до момента, когда истёкший access token обновляют, называя, у какой стороны на каждом шаге находится каждая учётная единица.

Готово, когда: вы можете сказать, сколько access token остаётся действительным и что происходит с запросом в полёте, когда он истекает.

## Частые ошибки

- **Хранение секрета клиента в браузере или мобильном приложении** — его прочтёт кто угодно; исправить: считайте клиент публичным и используйте поток, не требующий секрета.
- **Использование долгоживущего access token** — утечку нельзя ограничить сроком действия; исправить: держите access token коротким и обновляйте его.
- **Использование потока client credentials от имени пользователя** — личность сервиса подменяет личность пользователя; исправить: используйте поток, в котором участвует пользователь.
- **Трактовка области доступа как роли** — узкое разрешение принимают за ограниченные полномочия; исправить: держите решения об авторизации отдельно от разрешения.
- **Работа с паролем пользователя внутри клиента** — он оказывается под ударом собственных багов клиента; исправить: отправляйте пользователя на сервер авторизации.
