## Пример 1 — Обход, который превращается в запрос на строку

Экран операций перечисляет все открытые заказы и отправляет напоминание их клиенту. Код читается как две инструкции, но вторая выполняется раз на заказ, и экран замедляется по мере роста списка. Уберите повторяющуюся инструкцию и покажите доказательство, что она исчезла.

```py
orders = session.all("select * from orders where status = 'open'")

for order in orders:
    send_reminder(order.customer.email)
```

### Решение

```py
orders = session.all(
    "select o.id, c.email from orders o"
    " join customers c on c.id = o.customer_id"
    " where o.status = 'open'"
)

for order in orders:
    send_reminder(order.email)

# журнал инструкций
# select o.id, c.email from orders o join customers c ... -> 1 инструкция, 214 строк
```

Связь загружается вместе с исходным запросом, поэтому число инструкций больше не растёт с размером списка; доказательство — строка журнала, поскольку код выглядел бы почти так же и в другом случае. Включать журналирование инструкций при разработке — привычка, которая находит этот класс дефектов раньше боевой среды. Обычно ошибаются тем, что переносят цикл, а не загрузку: обход прячется внутри вспомогательной функции или сериализатора, и лишний запрос появляется там, где код экрана о нём не упоминает.

## Пример 2 — Перенос записи внутрь её транзакции

Оформление заказа добавляет строку заказа, резервирует товар и делает запись в реестре. Все три должны удаться или провалиться вместе, но сброс отображателя происходит до двух из них, а фиксация — после возврата из функции. Поставьте границу туда, где код её заявляет.

```py
def place_order(cart):
    session.add(Order(cart.id))
    session.flush()              # вставка выдаётся здесь

    stock.reserve(cart.items)
    ledger.record(cart.total)

# вызывающий фиксирует гораздо позже, после отправки ответа
```

### Решение

```py
def place_order(cart):
    with session.transaction():  # сброс ниже происходит внутри этого блока
        session.add(Order(cart.id))
        session.flush()          # вставка выдана, но ещё не зафиксирована

        stock.reserve(cart.items)
        ledger.record(cart.total)
    # фиксация при выходе из блока; сбой выше не сохранит ни одну из трёх

# сессия завершается вместе с запросом, поэтому карта идентичности её не переживает
```

Явный блок означает, что резерв и запись в реестре нельзя зафиксировать без заказа, а сбой до конца блока не оставляет частичного состояния. Ограничение сессии одним запросом важно по той же причине: долго живущая сессия переиспользует устаревшие объекты и растёт без предела. Обычно ошибаются, предполагая, что сброс совпадает со строкой, которая его вызвала, и потому ставят транзакцию вокруг кода, который уже записал данные.
