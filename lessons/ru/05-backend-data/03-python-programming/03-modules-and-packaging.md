## Что это такое

Модуль — это файл с определениями; пакет — каталог модулей. Импорт запускает модуль и привязывает его содержимое к имени. Вокруг этого стоят инструменты, делающие код доступным другим: виртуальное окружение, изолирующее зависимости проекта, список зависимостей, который их записывает, и метаданные упаковки, описывающие, как сам проект собирается и устанавливается.

## Почему это важно

Почти каждый случай «у меня работает» в Python происходит из-за окружения, а не из-за кода: двум проектам нужны разные версии одной библиотеки, системный интерпретатор трогать нельзя, зависимость поставили для теста и не записали. Виртуальные окружения и записанный список зависимостей убирают эту неоднозначность. Система импорта важна по другой причине: импорт исполняет файл, поэтому импорт с побочным эффектом на уровне модуля превращает граф зависимостей в последовательность действий, и потому сбои запуска в Python часто оказываются проблемой импорта.

## Ключевые идеи

### Виртуальное окружение изолирует зависимости одного проекта

Оно создаёт каталог с интерпретатором и собственным набором установленных пакетов, поэтому установка или обновление библиотеки затрагивает только этот проект. Активация меняет, какой интерпретатор запускается. Без окружения пакеты накапливаются в системном интерпретаторе, пока какая-нибудь пара проектов не станет взаимно несовместимой и ни один из них нельзя будет починить аккуратно.

```text
project/.venv/bin/python -m pip install -r requirements.txt
```

### Список зависимостей нужно записывать, лучше с версиями

Незаписанная зависимость работает ровно до тех пор, пока проект не начнёт собирать кто-то другой. Запись прямых зависимостей и их версий делает сборку воспроизводимой; фиксация всего транзитивного набора делает её точной. И то и другое лучше комментария в readme со списком того, что автор случайно запомнил.

### Импорт исполняет модуль

Операторы верхнего уровня модуля выполняются при первом его импорте и только тогда; последующие импорты переиспользуют уже загруженный модуль. Это кэширование объясняет, почему побочный эффект на уровне модуля случается один раз, сколько бы мест его ни импортировало, и почему циклический импорт может падать в зависимости от того, какой модуль импортирован первым.

### Защита `main` делает файл и модулем, и программой

Код под проверкой `if __name__ == "__main__":` выполняется только когда файл запущен напрямую, а не когда импортирован. Точка входа там означает, что файл можно использовать ради его определений, не запуская программу, — именно это делает его тестируемым.

### Пакеты — это каталоги с ясной публичной поверхностью

Импорт из пакета вносит его подмодули в область видимости, и то, что пакет открывает наружу, — это его интерфейс к остальному проекту. Небольшая поверхность — несколько имён, намеренно реэкспортированных, — означает, что внутренние перестройки не расходятся по всем вызывающим.

### Метаданные упаковки описывают то, что распространяется

Проект, который устанавливают, а не просто запускают, объявляет своё имя, версию и зависимости и может объявить точку входа, чтобы его можно было запускать как команду. Это превращает скрипт, который может запустить только автор, в то, что поставит коллега. Это стоит делать, когда код делится с другими, и это лишняя церемония, когда нет.

Два модуля, импортирующие друг друга, — обычно один замысел, разделённый не там, где нужно, или общая часть, которой место в третьем модуле. Отложенный внутрь функции импорт перестаёт давать сбой, но не убирает цикл, поэтому саму структуру всё ещё стоит пересмотреть.

## Практика

### Изолируйте зависимости проекта

Создайте виртуальное окружение для небольшого проекта, установите в него зависимости и запишите их с версиями.

Готово, когда: второе окружение, собранное по записанному списку, запускает проект так же.

### Сделайте скрипт импортируемым

Возьмите скрипт, логика которого выполняется при импорте, и спрячьте точку входа за защитой `main`, открыв остальное как функции.

Готово, когда: импорт файла не выполняет никакой работы, а его функции можно вызвать из теста.

## Частые ошибки

- **Установка в системный интерпретатор** — проекты становятся взаимно несовместимыми, и инструменты самой операционной системы могут сломаться; исправить: используйте виртуальное окружение для каждого проекта.
- **Запись зависимостей по памяти** — сборка не воспроизводима ни для кого, кроме вас; исправить: записывайте версии и фиксируйте транзитивный набор.
- **Работа на уровне модуля** — импорт файла её выполняет, а циклы дают запутанные сбои запуска; исправить: держите импорты без побочных эффектов и используйте защиту `main`.
- **Открытие каждого подмодуля наружу** — внутренние изменения расходятся по вызывающим; исправить: задайте небольшую публичную поверхность.
- **Отложенный импорт, скрывающий цикл** — структурная проблема остаётся; исправить: вынесите общую часть в отдельный модуль.
