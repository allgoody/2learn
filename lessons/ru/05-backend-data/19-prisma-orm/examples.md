## Пример 1 — Проследите связь от сгенерированного типа

Список операций показывает каждый открытый заказ с адресом электронной почты его клиента. Схема ниже описывает модели, а следующий за ней код обходит связь внутри цикла. Напишите запрос так, чтобы связь приходила вместе со списком, затем покажите доказательство, что была выдана только одна инструкция.

```prisma
model Order {
  id         Int      @id
  status     String
  customer   Customer @relation(fields: [customerId], references: [id])
  customerId Int
}

model Customer {
  id     Int     @id
  email  String
  orders Order[]
}
```

### Решение

```ts
const orders = await db.order.findMany({
  where: { status: "open" },
  include: { customer: true },   // разрешается в исходном запросе
});

for (const order of orders) {
  notify(order.customer.email);  // ни одной инструкции на заказ
}

// журнал сгенерированных инструкций (одна инструкция на весь список):
// SELECT "order".*, "customer".*
// FROM "Order" JOIN "Customer" ON "order"."customerId" = "customer"."id"
// WHERE "order"."status" = 'open'
```

Поскольку файл схемы — источник истины и для типов, и для базы данных, форма включённой связи входит в тип результата, поэтому обращение к свойству компилируется, а журнал инструкций подтверждает, что связь разрешена один раз, а не по разу на строку. Журнал здесь — единственная надёжная проверка: код выглядел бы почти так же, соединил бы клиент или запрашивал построчно. Обычно ошибаются, включая одну связь в исходный запрос и обходя затем другую внутри цикла, что возвращает тот же шаблон на уровень ниже.

## Пример 2 — Переименование, которое сгенерированная миграция удаляет

Поле переименовано в схеме с `fullName` на `name`. Этап генерации создаёт миграцию, применение которой в напечатанном виде потеряло бы каждое существующее имя. Прочитайте миграцию, решите, что она сделает с данными, и исправьте её до применения.

```text
изменение схемы: Customer.fullName -> Customer.name

сгенерированная миграция:
  ALTER TABLE "Customer" DROP COLUMN "fullName";
  ALTER TABLE "Customer" ADD COLUMN "name" TEXT;
```

### Решение

```sql
-- прочитано и исправлено вручную до применения миграции
ALTER TABLE "Customer" RENAME COLUMN "fullName" TO "name";
```

Инструмент видит только то, что одно поле исчезло, а другое появилось, поэтому выражает переименование как удаление и добавление; отревьюенная версия сохраняет столбец, его значения и любой индекс, который на него ссылался, а модель и база данных всё равно приходят в соответствие. Этап генерации также должен выполняться при сборке: пропущенная генерация компилируется против устаревшего клиента или просто падает. Обычно ошибаются, относясь к сгенерированной миграции как к артефакту для применения, а не как к коду для чтения.
