## Пример 1 — Любое сообщение принимают за ответ

Клиент ниже отправляет команду и предполагает, что следующее пришедшее сообщение отвечает на неё. Сервер также проталкивает уведомления, поэтому команды и push-сообщения чередуются и вызывается не тот обратный вызов. Дайте клиенту собственную схему сопоставления, чтобы ответ связывался с командой, которая его вызвала.

```js
socket.onmessage = (event) => {
  const message = JSON.parse(event.data);
  showReply(message);            // push и ответ здесь выглядят одинаково
};
```

### Решение

```js
const pending = new Map();

function send(type, payload) {
  const id = crypto.randomUUID();
  socket.send(JSON.stringify({ id, type, payload }));
  return new Promise((resolve) => pending.set(id, resolve));
}

socket.onmessage = (event) => {
  const message = JSON.parse(event.data);
  const resolve = pending.get(message.id);
  if (!resolve) return;         // незапрошенный push, а не ответ
  pending.delete(message.id);
  resolve(message.payload);
};
```

Без сопоставления «запрос — ответ» сообщение нельзя связать с запросом, который его вызвал, поэтому клиент несёт идентификатор в полезной нагрузке, а сервер возвращает его обратно — такова цена этой модели. Сокет был открыт запросом на обновление, в котором пользователь прошёл аутентификацию, поэтому аутентификация решается один раз, а сопоставление выполняется на каждом сообщении. Ошибка — предполагать, что порядок даёт связь, что ломается в первый же раз, когда сервер заговорит сам.

## Пример 2 — Переподключение, которое заваливает сервер

Клиент ниже переподключается в тот же миг, как соединение закрылось, и продолжает так, будто ничего не пропустил. После перезапуска все клиенты делают это в один и тот же момент. Перепишите путь переподключения так, чтобы повтор был распределён, а клиент узнавал, что пропустил.

```js
function connect() {
  socket = openSocket();
  socket.onclose = connect;     // сразу же и без восстановления
}
```

### Решение

```js
let attempt = 0;
let lastSeen = 0;

function connect() {
  const socket = openSocket();
  socket.onmessage = (event) => {
    lastSeen = event.data.sequence;
    render(event.data);
  };
  socket.onopen = () => {
    attempt = 0;
    replay(lastSeen);           // из надёжного хранилища, а не из сокета
  };
  socket.onclose = () => {
    const wait = Math.min(30000, 500 * 2 ** attempt) + Math.random() * 500;
    attempt += 1;
    setTimeout(connect, wait);
  };
}
```

Каждое открытое соединение держит один процесс, поэтому развёртывание или падение его сбрасывает и всё, отправленное за это время, пропадает; `replay` — то, что просит у надёжного хранилища сообщения после `lastSeen`. Экспоненциальная задержка с разбросом не даёт всем клиентам повторить попытку в одну и ту же секунду, что в плотном цикле превращается в поток запросов, который клиенты обрушивают на себя сами. Обычно ошибаются, полагая, что сообщение, отправленное пока клиент был офлайн, придёт позже, и потому не строят путь догона.
