## Что это такое

Контрактное тестирование проверяет, что реализация и описание API всё ещё совпадают. Описание рассматривается как контракт; тесты либо отправляют настоящие запросы к запущенному сервису и проверяют ответы по документу, либо порождают формы запросов и ответов из него и убеждаются, что сервер их принимает и выдаёт. В обоих случаях расхождение становится упавшей сборкой, а не обращением в поддержку.

## Почему это важно

Спецификация, которую никто не проверяет, — это документация, а документация расходится. Как только реализацию правят без документа, сгенерированный клиент перестаёт компилироваться, а опубликованная документация начинает врать. Контрактные тесты делают это расхождение видимым в момент его появления, когда исправление — однострочная правка схемы, а не в момент, когда сломался клиент. Они и есть механизм, делающий утверждение о единственном источнике из предыдущего урока правдой.

## Ключевые идеи

### Документ — это утверждение, а не побочный продукт

Генерация документации из аннотаций в коде даёт описание того, что код делает, включая его случайности. Рассмотрение документа как источника и проверка кода по нему даёт описание того, что API обещает. Первое удобно и не способно поймать ошибку; второе может.

```text
документ (источник истины) -> проверка живых ответов -> успех или провал
```

### Проверяйте настоящие ответы по схемам

Запрос к запущенному сервису и проверка тела и кода ответа по схеме ловят переименованное поле, расширенный тип или изменённый код. Запуск этого для каждой описанной операции даёт покрытие, соответствующее документу, а не воображению автора теста.

### Схемы должны быть строгими к неожиданным полям

Валидатор, игнорирующий неизвестные поля в ответе, не заметит вновь добавленное поле, а это часто передний край ломающего изменения. Явный ответ на вопрос, допустимы ли дополнительные поля, превращает документ ещё и в инструмент затягивания гаек, а не только в проверку.

### Контракты, движимые потребителем, проверяют обратное направление

То, что производитель проверил собственные ответы, доказывает соответствие API его описанию, а не то, что клиенты довольны. При подходе, движимом потребителем, каждый клиент публикует отправляемые им запросы и требуемые ответы, и сборка производителя падает, если она сломает известного потребителя. Так удаления полей ловятся до выпуска, а не после.

### Контрактные тесты быстры и должны идти на каждое изменение

Поскольку они проверяют формы интерфейса, а не поведение целиком, они достаточно дешевы, чтобы запускаться на каждом коммите, — а именно там они и полезнее всего. Проверка контракта, идущая ночью, находит расхождение на день позже; та, что идёт на запросе на слияние, находит его до слияния.

### Версионирование и контракты — одна дисциплина

Контрактный тест делает случайное ломающее изменение невозможным выпустить незаметно. Там, где изменение ломающее намеренно, версия поднимается осознанно, а старый контракт продолжает соблюдаться, пока не закроется окно устаревания. Тест — то, что обеспечивает соблюдение этого расписания.

## Практика

### Проверяйте ответы по документу

Напишите тест, который отправляет запрос для каждой описанной операции и проверяет каждый ответ по его схеме, включая ответы с ошибкой.

Готово, когда: изменение поля ответа в реализации без правки документа валит тест.

### Обнаружьте недокументированное добавление

Добавьте поле в ответ, не объявив его, и убедитесь, что проверка его находит.

Готово, когда: лишнее поле обнаружено, и вы решили, должна ли схема запрещать дополнительные свойства.

## Частые ошибки

- **Генерация документа из кода под видом контракта** — описание следует за ошибками, а не предотвращает их; исправить: считайте документ источником и проверяйте по нему.
- **Проверка только успешных ответов** — форма ошибки расходится незаметно; исправить: проверяйте каждый описанный ответ.
- **Молчаливое разрешение неизвестных полей** — неожиданные добавления проходят; исправить: решите и обеспечьте, допустимы ли дополнительные поля.
- **Редкий запуск проверок контракта** — расхождение находится после выпуска; исправить: запускайте их на каждое изменение.
- **Проверка только собственных обещаний производителя** — требования потребителя остаются непроверенными; исправить: применяйте контракты, движимые потребителем, там, где клиенты известны.
