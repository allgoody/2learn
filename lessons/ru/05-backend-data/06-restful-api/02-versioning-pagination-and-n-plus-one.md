## Что это такое

Проблемы, которые появляются, когда у API есть пользователи и данные. Опубликованное поле нельзя убрать, не сломав кого-нибудь, поэтому интерфейс должен уметь меняться; коллекция вырастает за пределы того, что можно вернуть одним ответом, поэтому её нужно разбивать на страницы; а ответ, вкладывающий связанные ресурсы, соблазняет сервер выдавать по одному запросу на родителя, так что его стоимость растёт вместе с результатом. Ничего из этого не видно в первый день жизни API, и всё это гораздо дешевле заложить заранее.

## Почему это важно

Эти три вещи дают большую долю жалоб на API, который был корректен на момент выпуска. Ломающее изменение заставляет всех клиентов обновиться разом, что для публичного API практически невозможно; коллекция без пагинации в конце концов упирается в тайм-аут или исчерпывает память; а эндпоинт, число запросов у которого растёт с числом строк, работает на тестах и падает в продакшене на первом же крупном аккаунте. Каждое из этого — решение проектирования с окном, в котором оно дёшево.

## Ключевые идеи

### Добавление безопасно, вычитание — нет

Добавление необязательного поля или нового эндпоинта не ломает существующих клиентов; удаление или переименование поля, смена типа или изменение смысла значения — ломает. Большая часть того, что выглядит давлением версий, на самом деле — неспособность делать изменения аддитивными. Там, где ломающего изменения не избежать, версия в адресе или в заголовке даёт старым клиентам неизменённый путь, пока новые переходят дальше.

```text
добавить поле               -> безопасно
сделать поле обязательным   -> ломает
расширить тип               -> безопасно, если старые значения означают то же
```

### Устаревание — это график, а не объявление

Поле, которое предстоит удалить, нужно пометить, задокументировать, отследить по фактическому использованию и только затем удалить. Отслеживание — та часть, которую обычно пропускают, и именно она говорит, сломается ли кто-нибудь. Отправка заголовков об устаревании и наблюдение за трафиком в течение полного цикла самого медленного клиента — то, что делает удаление безопасным.

### Пагинация должна быть и в ответе, и в запросе

Коллекция со страницами должна сообщать, как получить следующую, и в идеале насколько она велика. Пагинация со смещением проста и становится неточной по мере изменения данных, а пагинация по курсору остаётся стабильной и предпочтительна для больших или быстро меняющихся коллекций. Выбор особенно важен там, где дубликаты и пропуски недопустимы, например в ленте.

### Страница всегда должна быть ограничена

API, принимающий неограниченный размер страницы, находится в одном запросе от исчерпания памяти сервера. У предела должен быть максимум, который сервер обеспечивает сам, а не такой, который клиент обещает соблюдать. Это решение в одну строку предотвращает целый класс инцидентов.

### Запросы N+1 рождаются из формы ответа

Сериализация списка элементов и получение для каждого его связанных записей выдаёт по одному запросу на элемент. На десяти строках это незаметно, на десяти тысячах — смертельно, и это следствие того, где загружаются данные, а не базы данных. Лечится это загрузкой связанных записей для всей страницы одним запросом или возвратом идентификаторов, чтобы клиент сам запросил связанную коллекцию.

### Форма ответа — это контракт о стоимости

Включение каждого связанного объекта в каждый ответ делает один вызов удобным и делает эндпоинт дорогим для клиентов, которым нужны только идентификаторы. Предсказуемое правило — коллекция содержит идентификаторы, детальный ответ содержит объект, связанные коллекции — отдельные адреса — держит и полезную нагрузку, и число запросов под контролем.

## Практика

### Спроектируйте контракт страниц

Возьмите эндпоинт коллекции и дайте ему ограниченный размер страницы, ссылку на следующую и явное упорядочение.

Готово, когда: запрос страницы больше максимума обрезается до максимума, а переход по следующей ссылке дважды возвращает каждый элемент ровно один раз, даже когда добавляются новые.

### Найдите и исправьте запрос N+1

Возьмите эндпоинт, возвращающий список со связанными данными, посчитайте, сколько запросов он выдаёт, и измените его так, чтобы связанные записи для всей страницы загружались одним запросом.

Готово, когда: число запросов больше не растёт с числом элементов на странице.

## Частые ошибки

- **Удаление или переименование поля на месте** — все существующие клиенты ломаются разом; исправить: добавьте замену, объявите старое устаревшим, отследите его использование, затем удалите.
- **Приём неограниченного размера страницы** — один запрос может исчерпать сервер; исправить: обеспечьте максимум на стороне сервера.
- **Пагинация со смещением по быстро меняющимся данным** — элементы пропускаются или дублируются между страницами; исправить: используйте курсор для нестабильных коллекций.
- **Сериализация вложенных данных по элементу** — число запросов растёт со страницей; исправить: загружайте связанные данные пакетом.
- **Возврат всего в каждом ответе** — полезная нагрузка и стоимость запросов растут вместе; исправить: определите, что включает каждый эндпоинт.
