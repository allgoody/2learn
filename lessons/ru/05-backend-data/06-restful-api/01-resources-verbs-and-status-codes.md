## Что это такое

Правила проектирования RESTful API: называйте вещи, а не действия; используйте методы протокола в том смысле, для которого они определены; сообщайте результат точным кодом состояния. Ресурс — это существительное с адресом; метод говорит, что с ним делать; код состояния говорит, что произошло. Последовательное следование этим трём — большая часть того, что делает API приятным в использовании.

## Почему это важно

API — интерфейс с долгой жизнью, и именно его соглашения позволяют написать клиента, не читая спецификацию от корки до корки. Когда правила соблюдены, одна и та же форма запроса работает для нового ресурса и одна и та же обработка ошибок — для нового сбоя. Когда их нарушают — чтение, которое удаляет, создание, которое читает, ошибка, возвращающая код успеха, — клиентам приходится делать особый случай для каждого эндпоинта, и эти ошибки дорого исправлять, когда API уже в работе.

## Ключевые идеи

### Называйте ресурсы, а не операции

Адрес должен обозначать вещь, а не действие над ней. Адрес коллекции перечисляет вещи; дочерний адрес обозначает одну; вложенный адрес обозначает что-то, принадлежащее другой вещи. Действия, не отображающиеся на метод, можно смоделировать как подчинённый ресурс, например возврат по платежу, а не добавлять их в путь глаголом.

```text
GET  /orders            -> список
GET  /orders/42         -> один заказ
POST /orders            -> создание
GET  /orders/42/items   -> позиции одного заказа
```

### Используйте методы в их определённом смысле

Чтение безопасно и повторяемо; создание — нет; замена всей вещи по заданному адресу повторяема; удаление повторяемо по результату. Посредники, повторные попытки и предзагрузчики предполагают именно эти значения. Эндпоинт, который меняет состояние при чтении, сработает из-за предпросмотра ссылки или обходчика, а тот, что создаёт вторую запись при повторе, будет плодить дубликаты при каждом сбое сети.

### Коды состояния — машинно-читаемый результат

Успех означает, что запрос понят и выполнен; перенаправление — что смотреть нужно в другом месте; ошибка клиента — что неверен сам запрос и повтор не поможет; ошибка сервера — что запрос может быть верным и повтор может помочь. Выбор конкретного кода внутри семейства несёт информацию, по которой клиент может действовать: ошибка валидации — не то же, что ошибка аутентификации, а она — не то же, что отсутствующий ресурс.

### Создание возвращает, где теперь живёт вещь

Успешное создание должно указать новый ресурс в заголовке и обычно вернуть его представление. Это позволяет клиенту продолжить без второго запроса и без угадывания идентификатора. Возврат одного лишь флага успеха заставляет каждого клиента опрашивать или самому конструировать адреса.

### Идемпотентность — свойство, которое проектируют, а не совпадение

Повторяемую операцию можно безопасно повторить после тайм-аута; неповторяемую — нельзя. Для созданий, которые приходится повторять, — платежа, заказа — клиент передаёт ключ, а сервер его записывает, поэтому вторая попытка с тем же ключом возвращает первый результат, а не выполняет работу дважды. Это разница между системой, переживающей нестабильную сеть, и системой, списывающей деньги дважды.

### Ошибки должны быть единообразными и содержательными

Каждый сбой должен использовать одну и ту же форму, называть поле или условие, которое не прошло, и включать код, по которому клиент может ветвиться, не разбирая текст. Единообразная форма ошибки означает один обработчик на клиенте; форма для каждого эндпоинта — по одному на эндпоинт. Это же делает журналы и дашборды единообразными, потому что один и тот же код появляется везде.

## Практика

### Смоделируйте один домен как ресурсы

Возьмите небольшой домен с тремя существительными и одну операцию, которая не укладывается в метод, и напишите адреса и методы для каждого.

Готово, когда: каждый адрес обозначает вещь, каждый метод соответствует своему определённому смыслу, а необычная операция имеет собственный ресурс.

### Добавьте идемпотентность созданию

Возьмите эндпоинт создания и добавьте ключ, который передаёт клиент, чтобы повторный запрос возвращал исходный результат, а не создавал вторую запись.

Готово, когда: отправка одного и того же запроса дважды с тем же ключом даёт одну запись и одинаковые ответы.

## Частые ошибки

- **Глаголы в пути** — адрес перестаёт обозначать вещь; исправить: смоделируйте операцию как ресурс или используйте правильный метод.
- **Изменение состояния при чтении** — обходчики и предзагрузчики выполнят это изменение; исправить: держите чтение безопасным и используйте метод, означающий изменение.
- **Код успеха в ответ на ошибку** — каждому клиенту нужен особый случай; исправить: используйте семейство статусов, соответствующее результату.
- **Неповторяемое создание без ключа** — повтор создаёт дубликат записи; исправить: принимайте ключ идемпотентности и возвращайте первый результат.
- **Свой формат ошибки на каждый эндпоинт** — у клиентов накапливаются парсеры; исправить: одна форма ошибки с кодом для ветвления.
