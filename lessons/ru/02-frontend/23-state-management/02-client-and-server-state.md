## Что это такое

Клиентское состояние — данные, которыми приложение владеет: какая вкладка открыта, несохранённый черновик, выбранный пользователем фильтр. Серверное состояние — данные, которые приложение одолжило: список заказов, профиль пользователя, остаток на складе. В коде они похожи — и то, и другое вы читаете и отображаете, — но это разные задачи, потому что сервер может изменить значение, не сообщив вам.

## Почему это важно

Обращение с серверными данными как с обычным состоянием порождает свой набор багов: устаревший список после того, как запись изменил другой пользователь, страница, показывающая спиннер при каждом визите, потому что ничего не сохранили, и кэш, который никогда не инвалидируется. Исправление — не хранилище побольше; это признание того, что серверное состояние — кэш со сроком годности и политикой обновления. Как только это различие сделано, вопросы становятся конкретными — сколько это может оставаться устаревшим, что его инвалидирует, что показывать, пока оно обновляется, — и целый класс написанных вручную флагов загрузки исчезает.

## Ключевые идеи

### Серверные данные — кэш, а не источник правды

Держите копию ради скорости, но помните, чья это копия. Каждому кэшированному значению нужны три ответа: когда его загрузили, что делает его устаревшим и что делать, когда оно такое. Кэш без срока годности и без инвалидации — баг с длинным запалом.

```js
// Запись кэша осмысленна только вместе с её возрастом и триггером
{ data, fetchedAt: Date.now(), key: "orders:page=1" }
```

### Ключуйте каждый запрос по его входным данным

Два запроса к одному ресурсу с разными параметрами — разные записи кэша. Ключ по входным данным — запросу, странице, фильтру — позволяет ответить «у нас это уже есть?» до загрузки и инвалидировать точно, а не всё подряд.

### Моделируйте запрос, а не три флага

Единое объединение — loading, ready, error и состояние обновления поверх ready — делает противоречивые комбинации невозможными. Три булевых значения допускают экран, который одновременно загружается, содержит ошибку и имеет данные, — ровно то, что видят пользователи, когда флаги расходятся.

```ts
type Query<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "error"; error: Error }
  | { status: "ready"; data: T; stale: boolean };
```

### Инвалидируйте после изменения — осознанно

После записи кэшированные копии того, что затронула запись, неверны. Варианты — повторно запросить затронутые запросы, записать в кэш новое значение из ответа сервера или пометить затронутые записи устаревшими и обновить их в фоне. Назвать затронутые ключи — и есть работа; остальное механично.

### Показывайте старое значение, пока идёт обновление

Список, который при каждом обновлении схлопывается в спиннер, хуже списка, который остаётся на месте с неприметной пометкой «обновляется». Именно поэтому состояние ready несёт флаг `stale`, а не возвращается в loading: так предыдущие данные остаются видимыми во время фонового обновления.

### Позвольте библиотеке делать это, если проект позволяет

Специализированные библиотеки серверного состояния реализуют кэширование, дедупликацию, повторные попытки, фоновое обновление и инвалидацию. Написать это вручную — отдельный проект. Важно знать модель, чтобы использование такой библиотеки было решением, а не зависимостью.

## Практика

### Разделите состояние одного экрана на два вида

Возьмите экран, который загружает список и позволяет пользователю его фильтровать. Выпишите каждое значение, которое он держит, и отметьте каждое как клиентское или серверное состояние.

Готово, когда: список, его состояние загрузки и его состояние ошибки — серверное состояние с одним ключом кэша, фильтр и сортировка — клиентское состояние, и ни одно значение не делает обе работы.

### Сделайте изменение инвалидирующим точно

Добавьте в список действие удаления. После его успеха обновите кэш, а не запрашивайте всё заново, и убедитесь, что затронутое представление верно без полной перезагрузки.

Готово, когда: удаление строки сразу обновляет список, а последующая навигация показывает текущее состояние сервера, а не старую закэшированную версию.

## Частые ошибки

- **Хранение загруженных данных там же, где состояние формы** — у них разные сроки жизни и правила инвалидации, и после повторной загрузки форма начинает врать; исправить: держите серверные данные в кэше с ключом по запросу, а клиентское состояние — там, где его редактируют.
- **Кэш, который никогда не инвалидируется** — пользователь не видит чужих записей; исправить: инвалидируйте при изменении и при фокусе окна или задайте явное время устаревания.
- **Перезагрузка всего после каждой записи** — страница мерцает, а сеть полна запросов, возвращающих одни и те же данные; исправить: обновляйте затронутые записи кэша.
- **Спиннер при каждом обновлении в полёте** — экран пустеет при каждом опросе, и пользователь теряет место; исправить: сохраняйте предыдущее значение и показывайте обновление отдельно.
- **Написанные вручную флаги загрузки, ошибки и данных** — комбинации противоречат друг другу; исправить: моделируйте запрос одним объединением.
