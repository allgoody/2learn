## Что это такое

Внедрение зависимостей — это приём, при котором класс просит то, что ему нужно, вместо того чтобы конструировать это сам: компонент объявляет зависимость от сервиса, а экземпляр поставляет фреймворк. RxJS — библиотека для составления асинхронных потоков значений с помощью операторов. Angular использует первое, чтобы связывать приложение, а второе — чтобы представлять данные, приходящие во времени: ответы HTTP, ввод в форму, сообщения WebSocket.

## Почему это важно

На эти две идеи приходится почти всё, что кажется непривычным в кодовой базе на Angular. Внедрение зависимостей делает сервисы тестируемыми: тест может подставить заглушку так, что класс об этом не знает, — и превращает разделение состояния между компонентами в поставку одного экземпляра в нужном месте. RxJS превращает неудобные части асинхронной работы — отмену, повтор, подавление дребезга, объединение двух источников — в composable-операторы, а не во вложенные колбэки. Вместе они объясняют форму кода, которую иначе трудно прочитать со стороны.

## Ключевые идеи

### Сервисы — это просто классы, где-то предоставленные

Сервис — обычный класс на TypeScript с декоратором `@Injectable`. Регистрация в корневом внедрителе создаёт один общий экземпляр на всё приложение; регистрация на компоненте создаёт отдельный экземпляр на каждый экземпляр компонента — так две таблицы держат независимое состояние из одного класса.

```ts
@Injectable({ providedIn: "root" })
export class OrdersService {
  constructor(private readonly http: HttpClient) {}

  list(): Observable<Order[]> {
    return this.http.get<Order[]>("/api/orders");
  }
}
```

### Просите зависимость в конструкторе

Список параметров конструктора — это объявление того, что нужно классу, а внедритель разрешает его по типу. Так граф зависимостей виден вверху файла, и тест может подставить подделку, не меняя класс.

### Observable — это поток, а не промис

Промис разрешается один раз; observable может испустить ноль, одно или много значений и не делает ничего, пока кто-нибудь не подпишется. Из-за этой разницы HTTP-вызов — холодный observable: вызов метода сервиса не отправляет запрос, пока значение не запросит пайп `async` в шаблоне или ручная подписка.

```html
@if (orders$ | async; as orders) {
  <ul>
    @for (order of orders; track order.id) { <li>{{ order.id }}</li> }
  </ul>
}
```

### Операторы описывают преобразование

`map`, `filter`, `debounceTime`, `switchMap`, `catchError` и `retry` — каждый описывает один шаг. `switchMap` важнее всех для поиска: он отписывается от предыдущего внутреннего observable, а это ровно та отмена, которая нужна полю поиска.

```ts
readonly results$ = this.query$.pipe(
  debounceTime(250),
  distinctUntilChanged(),
  switchMap((q) => this.http.get<Result[]>(`/api/search?q=${encodeURIComponent(q)}`)),
  catchError(() => of([]))
);
```

### Отписывайтесь сами или позвольте это фреймворку

Ручную подписку в компоненте нужно отменить в `ngOnDestroy`, иначе компонент живёт столько же, сколько поток. Пайп `async` и `takeUntilDestroyed` делают это за вас — поэтому им и предпочитают голый `subscribe`.

### Держите состояние в потоке, где можете

Вывод представления из observable — объединяя их через `combineLatest` или отображая селектор хранилища — избавляет от дублированного состояния, которое появляется, когда те же данные ещё и скопированы в поле компонента. Там, где состояние всё же нужно держать, держите его в одном сервисе и выставляйте observable.

## Практика

### Соберите поиск с отменой

Создайте поле поиска, значение которого — observable, подавите дребезг и через `switchMap` отправьте HTTP-запрос. Печатайте быстро.

Готово, когда: на панели сети видно, что ранние запросы отменены, а список никогда не отрисовывает результаты запроса, который уже не текущий.

### Разделите состояние через предоставленный сервис

Поместите счётчик и метод его увеличения в сервис, предоставленный в корне. Прочитайте его из двух соседних компонентов.

Готово, когда: оба компонента показывают одно значение и оба сразу обновляются, когда любой из них его увеличивает, без входов и выходов между ними.

## Частые ошибки

- **Подписка без отписки** — компонент протекает и продолжает получать события после своего исчезновения; исправить: используйте пайп `async` или отменяйте через `takeUntilDestroyed`.
- **Использование `mergeMap` для поиска** — запрос на каждое нажатие сохраняется, и медленный ранний ответ может победить; исправить: используйте `switchMap`, чтобы новый запрос отменял предыдущий.
- **Предоставление сервиса на неверном уровне** — либо каждый компонент получает свою копию, либо все дерутся за одну; исправить: решите для каждого сервиса, общий он или на компонент, и регистрируйте там.
- **Копирование данных observable в поле компонента на каждой эмиссии** — два источника правды расходятся; исправить: выводите представление из потока.
- **Обращение с observable как с промисом** — без подписки ничего не происходит, а холодный observable повторяет свою работу на каждого подписчика; исправить: подпишитесь один раз на краю или разделите поток.
