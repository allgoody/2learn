## Пример 1 — Пауза вместо неизвестного объёма работы

Сквозной тест делает паузу после сохранения, а затем проверяет. На ноутбуке он проходит, в конвейере падает. Скажите, что эта задержка на самом деле угадывает, а затем замените её.

```ts
await page.getByRole("button", { name: "Save" }).click();
await page.waitForTimeout(3000);                       // ставка на быструю машину
await expect(page.getByText("Saved")).toBeVisible();
// конвейер: FAIL — иногда запись занимает 3.2s
```

### Решение

```ts
await page.getByRole("button", { name: "Save" }).click();
await expect(page.getByText("Saved")).toBeVisible({ timeout: 15_000 });
// проходит, как только состояние наступает; чётко падает, когда оно так и не наступает
```

Фиксированная пауза — это догадка о том, сколько времени занимает работа, и она терпит неудачу именно на более медленных машинах, где результат важен. Ожидание условия и быстрее, и надёжнее: оно возвращается в тот момент, когда состояние появляется, вместо того чтобы каждый раз сжигать задержку, а когда состояние так и не наступает, падает с сообщением, называющим пропущенное. Современные браузерные инструменты ждут автоматически для своих действий, но любое состояние, которое создаёт ваше приложение, всё равно требует явной проверки, на которой можно ждать, — пауза обычно и есть знак, что такой проверки нет.

## Пример 2 — Прогон, зависящий от данных предыдущего прогона

Тесты входят под пользователем, подготовленным однажды в общей тестовой среде. При параллельном запуске они сталкиваются, а повторная попытка скрывает отказ, не сохраняя улик. Сделайте набор независимым, а его отказы — диагностируемыми.

```text
подготовка: test-user@example.test / password
тест A: меняет отображаемое имя на "Ada"
тест B: проверяет, что отображаемое имя — "Test User"     -> падает при запуске с A
повтор: при отказе запускается снова -> зелёный -> ничего не сохранено
```

### Решение

```text
id прогона: e2e-20260301-7f3a
каждый аккаунт, созданный этим прогоном, содержит id прогона
при отказе: снимок экрана + трассировка + лог сервера, загружаются с id прогона
```

Уникальные для прогона данные — это то, что делает два прогона независимыми, выполняются ли они параллельно или в любом порядке, а идентификатор прогона делает очистку дешёвой, а отказ — проще для отслеживания. Повторная попытка — вторая половина проблемы: тест, которому она нужна дважды в неделю, имеет невыявленную гонку, поэтому собирайте улики при каждом отказе, повторялся он или нет. Отношение к частоте повторных попыток как к метрике ошибок — и к самому нестабильному тесту как к ошибке, которую нужно починить, а не как к помехе, которую нужно отложить в карантин, — вот что мешает зелёному цвету набора стать цветом, которому никто не верит.
