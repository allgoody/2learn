## Что это такое

GitHub — сервис хостинга, построенный поверх git, и он добавляет то, что нужно репозиторию, чтобы быть местом работы команды: удалённые репозитории, pull request'ы, задачи, права и автоматические проверки. Модель репозитория не меняется — удалённый репозиторий это просто ещё одна копия графа объектов, — но слой совместной работы — то место, где живёт большинство повседневных решений.

## Почему это важно

Слой совместной работы — это место встречи кода и разговора и место, где становятся видны соглашения команды. Pull request — единица ревью, площадка обсуждения дизайна и запись о том, почему изменение было принято. Задачи — это бэклог, а их связи с pull request'ами — история проекта. Права и защищённые ветки — то, что не даёт ошибке дойти до боя. Непрерывная интеграция тоже работает здесь, хотя сам конвейер — отдельная тема, разобранная в разделе об облаке и DevOps.

## Ключевые идеи

### Удалённый репозиторий — просто ещё один репозиторий

Пуш — это отправка объектов, которых нет у удалённого репозитория, а фетч — получение объектов, которых нет у вас. Не более того. Поэтому локальный репозиторий полностью работоспособен без сервера и поэтому роль удалённого — координация, а не власть. Это же объясняет, почему перезапись опубликованной истории разрушительна: удалённый репозиторий и каждая копия хранят объекты, на которые ваша локальная копия больше не ссылается.

```text
push:  отправить объекты, которых не хватает удалённому, затем сдвинуть ссылку ветки
fetch: получить новые объекты, затем обновить ссылку отслеживания
```

### Pull request — это разговор, прикреплённый к ветке

Открывая его, вы предлагаете слить одну ветку в другую и даёте всем место прочитать дифф, прокомментировать строки и одобрить. Это не возможность git: это способ хостинга прикрепить обсуждение и статус к ветке. Поскольку это единица ревью, именно короткая ветка и маленький дифф делают ревью полезным.

```text
feature/pricing -> main      ревью, комментарии, одобрение, слияние
```

### Задачи — это бэклог, а связи — история

Задача фиксирует проблему или запрос; pull request, который на неё ссылается, связывает их. Со временем связи — это то, как сопровождающий отвечает на вопрос «почему код такой?» — pull request хранит обсуждение, а задача хранит причину. Именно запись причины в задаче, а не в приватном чате, делает это возможным.

### Форки, ветки и права

Участники без права записи делают форк репозитория, пушат в свой форк и открывают pull request между ними. Для команды права на ветки и защищённые ветки — это ограждение: они могут требовать проходящую проверку и ревью перед слиянием и запрещать прямой пуш в основную линию. Форма модели прав решает, какая часть процесса обеспечивается принудительно, а не на доверии.

```text
main: защищена, требует 1 одобрение и зелёную проверку
участник: форк -> пуш в форк -> pull request
```

### Непрерывная интеграция работает здесь, но принадлежит другой теме

Хостинг прогоняет автоматические проверки против pull request'а — сборку, тесты, линтер — и докладывает результат в разговоре. Проектирование этих конвейеров, выбор runner'ов и управление секретами — отдельный навык, разобранный под облаком и DevOps вместе с инструментами автоматизации для репозиториев GitHub. Эта запись останавливается на том, что проверки появляются на pull request'е и могут быть обязательными до слияния.

```text
pull request: 1 проверка идёт -> 2 прошло -> кнопка слияния доступна
```

## Практика

### Проведите изменение через pull request

Создайте ветку, сделайте одно небольшое изменение, запушьте его и откройте pull request со ссылкой на задачу. Запросите ревью, ответьте на комментарий и слейте.

Готово, когда: pull request показывает связанную задачу, разговор ревью и слитый коммит, и вы можете назвать, что из этого добавил хостинг, а не git.

### Потребуйте проверку до слияния

В репозитории, который вы контролируете, защитите основную ветку так, чтобы pull request'у требовалось как минимум одно одобрение и одна проходящая проверка.

Готово, когда: прямой пуш в main отклоняется, а pull request без одобрения нельзя слить.

## Частые ошибки

- **Отношение к удалённому репозиторию как к единственной копии истины** — локальная работа останавливается вместе с сетью, а перезаписи истории путают всех; исправить: помните, что удалённый репозиторий — одна копия среди многих.
- **Pull request с огромным диффом** — рецензенты пробегают глазами, и дефекты проходят насквозь; исправить: держите ветки короткими и разделяйте несвязанные изменения.
- **Обсуждение дизайна в приватном канале** — рассуждение не доходит до репозитория; исправить: переносите вывод в pull request или в задачу.
- **Оставление основной ветки незащищённой** — ошибку можно запушить прямо в историю боя; исправить: требуйте ревью и проходящую проверку перед слиянием.
- **Смешение автоматизации хостинга с git** — репозиторий прекрасно работает без неё, а конвейер — отдельный навык; исправить: держите эти две темы раздельно и помещайте проектирование конвейера в раздел об облаке и DevOps.
