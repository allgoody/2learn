## Что это такое

SOLID — это пять правил объектного проектирования, собранные под одним акронимом Робертом Мартином. Это не законы и не всё проектирование целиком; это набор эвристик, указывающих на одну цель — удерживать изменение локальным, чтобы правка одной части системы не расходилась по частям, которые к ней отношения не имеют. Каждая буква называет один способ, которым структура кода пропускает изменение через границы.

## Почему это важно

Большая часть кода гниёт из-за связанности, а не из-за ошибок. Класс с двумя причинами для изменения означает, что каждый релиз рискует задеть вторую заботу; базовый класс с подклассом, который не может его соблюсти, означает, что вызывающим приходится проверять типы, о которых они не должны знать; модуль, который сам создаёт свои зависимости, нельзя ни протестировать, ни заменить. Эти проблемы не заявляют о себе. Они накапливаются правками, которые становятся всё крупнее, пока небольшой запрос функции не начинает занимать неделю. SOLID называет симптомы достаточно рано, чтобы исправить их дёшево.

## Ключевые идеи

### Единственная ответственность

У модуля должна быть одна причина для изменения, что обычно означает одну группу людей, которым он небезразличен. Класс, который форматирует счёт и ещё и отправляет его, меняется и когда меняется вёрстка, и когда меняются правила доставки — две причины, две команды, один файл. Проверка идёт не по числу методов, а по числу аудиторий, чьи запросы вызвали бы правку.

```ts
class Invoice { total() { /* ... */ } }
class InvoiceEmailer { send(invoice) { /* ... */ } }
```

### Открыт для расширения, закрыт для изменения

Проект должен позволять добавить новый случай добавлением кода, а не правкой растущей цепочки условий. На практике это значит зависеть от интерфейса в точке, где происходит варьирование, и подключать новые реализации на периферии. Это не значит «никогда не править файл» — это значит, что правка для нового случая должна быть в одном месте, а неразбросанной по многим.

```ts
interface ShippingRate { price(parcel): number }
class CourierA implements ShippingRate { /* ... */ }
class CourierB implements ShippingRate { /* ... */ }
```

### Подстановка Лисков

Если функция принимает базовый тип, любой подтип должен работать так, чтобы вызывающий не знал, какой именно он получил. Когда подкласс отвергает аргумент, который принимал родитель, или бросает исключение там, где родитель возвращал значение, каждому вызывающему теперь нужна проверка типа — и абстракция перестала себя оправдывать. Честные исправления — сделать иерархию более плоской или смоделировать различие как данные, а не как наследование.

```ts
class ReadOnlyList extends List {
  add(item) { throw new Error("только чтение"); }   // ломает всех вызывающих, которые используют List
}
```

### Разделение интерфейсов

Ни один вызывающий не должен зависеть от методов, которыми не пользуется. Широкий интерфейс заставляет каждого реализующего писать заглушки и заставляет вызывающих знать о посторонних операциях, поэтому изменение любого метода может сломать реализацию, которая его вовсе не трогала. Предпочитайте несколько маленьких интерфейсов, которые класс может реализовать вместе, и определяйте их с точки зрения вызывающего.

```ts
interface Reader { read(id): Record }
interface Writer { write(record): void }
```

### Инверсия зависимостей

Высокоуровневая политика не должна зависеть от низкоуровневых деталей; и то, и другое должно зависеть от абстракции. Когда доменный сервис сам создаёт клиент базы данных, домен приварен к этой библиотеке и не может быть протестирован без неё. Объявление зависимости параметром переворачивает направление, и вызывающий решает, какую реализацию предоставить.

```ts
class OrderService {
  constructor(private payments: PaymentGateway) {}
}
```

## Практика

### Найдите вторую причину для изменения

Выберите в своём коде класс с более чем десятком методов. Выпишите отдельные причины, по которым кто-то мог бы попросить его изменить. Если вы нашли больше одной аудитории, разделите его по этой линии.

Готово, когда: у каждого получившегося класса есть одно предложение, описывающее, почему он изменится, и тесты по-прежнему проходят.

### Подставьте зависимость в тесте

Возьмите сервис, который сам создаёт своего помощника, и измените его так, чтобы он получал этого помощника. Напишите тест, который подставляет подделку.

Готово, когда: тест выполняется без настоящего помощника, и ни одно место вызова в продакшене не изменило поведения.

## Частые ошибки

- **Применение каждого правила к каждому классу** — небольшие программы получают церемонии без пользы; исправить: применяйте правила там, где граница уже создаёт трение.
- **Чтение «открыт/закрыт» как «никогда не правь этот файл»** — в результате появляется слой плагинов для одной реализации; исправить: стремитесь к одному месту изменения на каждый новый случай.
- **Сокрытие сломанной иерархии за проверками типов** — `instanceof` у вызывающих — это запах того, что подстановка провалилась; исправить: переработайте абстракцию или смоделируйте варьирование как данные.
- **Разделение интерфейсов до трёх импортов в каждом месте вызова** — доведённое до крайности разделение само становится связанностью; исправить: определяйте интерфейсы из нужд вызывающего, а не по алфавиту методов.
- **Внедрение зависимостей, которые никогда не будут меняться** — параметр для чистой утилиты добавляет косвенность ни за что; исправить: инвертируйте только там, где правдоподобен тестовый двойник или вторая реализация.
