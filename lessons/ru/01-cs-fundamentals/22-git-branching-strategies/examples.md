## Пример 1 — Ветка функции, прожившая три недели

Команда держит по одной ветке на функцию, пока та не завершена. Ниже — запись о ветке, слитой в прошлом месяце. Скажите, чего стоила стратегия, и покажите ту же работу при коротких ветках.

```text
feature/new-checkout   ответвлена 3 недели назад
main                   +41 коммит с точки ветвления
merge                  -> 27 конфликтующих файлов, два дня правок
```

### Решение

```text
день 1  ветка от main, коммит первого среза
день 1  слияние в main за флагом: newCheckout=false
день 2  снова ветка от main для следующего среза
выпуск  переключить флаг; ни события слияния, ни ветки стабилизации
```

Короткие ветки держат поверхность интеграции маленькой, потому что два изменения встречаются на следующий день после написания каждого, а не через три недели. Незавершённая работа спрятана за флагом, поэтому `main` остаётся готовым к выпуску, а результат CI описывает нечто близкое к тому, что команда действительно строит. Плата — флаг нужно сопровождать и со временем убрать, что куда дешевле ручного разрешения трёхнедельного расхождения.

## Пример 2 — Стратегия, противоречащая процессу выпуска

Команда разворачивает любой зелёный коммит по нескольку раз в день, но приняла GitFlow, потому что так было в прошлой компании. Через два месяца `develop` ушёл на три недели вперёд от `main`. Разберите расхождение и назовите стратегию, которая действительно нужна процессу выпуска.

```text
main     ----o------------------o--->
              \                /
develop  ------o--o--o--o--o--o      3 недели вперёд
release                 o--o          единственный стабилизированный артефакт
```

### Решение

```text
main   ----o----o----o----o---->   всегда готов к выпуску
              \  /    \  /
               o       o           сливаются в течение дня

tag v1.4 на развёрнутом коммите; хотфикс от тега, слитый вперёд
```

Процесс выпуска решает стратегию, а не наоборот. Если развернуть можно любой коммит, ветке стабилизации нечего стабилизировать: ветка выпуска — этап, который процесс пропускает, а `develop` существует лишь затем, чтобы `main` выглядел устаревшим. Trunk-based development моделирует этот процесс напрямую, помечая развёрнутый коммит тегом, а не замораживая его. Отказ, которого нужно избегать, — смесь, о которой никто не договаривался: ветка выпуска здесь единственный артефакт, который кто-либо тестирует, а это ровно то расхождение, которое стратегия должна была предотвратить.
