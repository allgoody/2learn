## Пример 1 — Сборка отчёта по одному этапу за раз

Файл журнала хранит один запрос на строку, а седьмое поле, разделённое пробелами, — это эндпоинт. Цель — пять самых частых эндпоинтов с их количеством, причём ошибки не должны попасть в результаты. Этапы ниже запускаются по одному. Скажите, что добавляет каждый и почему ошибки были отделены.

```bash
cut -d' ' -f7 access.log           # один эндпоинт на строку
cut -d' ' -f7 access.log | sort    # одинаковые эндпоинты становятся соседями
... | uniq -c                      # считает каждый блок одинаковых строк
... | sort -rn                     # самые частые первыми
... | head -5                      # пять запрошенных
```

### Решение

```bash
cut -d' ' -f7 access.log 2> errors.txt \
  | sort | uniq -c | sort -rn | head -5

sort      сближает одинаковые эндпоинты, чтобы uniq -c мог посчитать блок
uniq -c   требует отсортированного ввода; на неотсортированном он даёт много мелких счётчиков
sort -rn  упорядочивает по числу, которое напечатал uniq
2> errors.txt  держит диагностику вне конвейера
```

Каждый этап — одно небольшое преобразование, и сборка слева делает неверное поле или флаг видимыми уже после первой команды, а не погребёнными в уверенном итоговом ответе. Сортировка перед подсчётом — тот шаг, который пропускают: `uniq` схлопывает только соседние одинаковые строки, поэтому на неотсортированном вводе один эндпоинт попадает в отчёт несколько раз с мелкими счётчиками. Ловушка — три потока: если бы диагностика делила стандартный вывод, в подсчёт попали бы мусорные строки.

## Пример 2 — Сбой, который выглядел как пустой результат

Скрипт считает сегодняшние ошибки и печатает число. Запуск ниже напечатал `0`, хотя файл журнала на самом деле отсутствовал. Скажите, что дало нуль, и перепишите скрипт так, чтобы сбой нельзя было прочитать как достоверный результат.

```bash
count=$(grep -c "ERROR" /var/log/app.log)
echo "ошибок: $count"
# ошибок: 0        <- файла не существует
```

### Решение

```bash
if count=$(grep -c "ERROR" /var/log/app.log); then
  echo "ошибок: $count"
else
  echo "не удалось прочитать журнал (код $?)" >&2
  exit 1
fi
```

Команда сообщает об успехе статусом завершения нуль, а о неудаче — чем угодно другим, и провалившийся `grep` всё равно записал `0` в стандартный вывод, поэтому скрипт не мог отличить спокойный день от отсутствующего файла. Проверка статуса первой снимает неоднозначность: путь сбоя говорит, что не удалось прочитать, и завершается ненулём, чтобы вызывающий это заметил. Ловушка в том, что число выглядит совершенно достоверным, поэтому неисправность всплывает гораздо позже как дашборд, который тихо показывал нуль.
