## Что это такое

Имя — это интерфейс между кодом и читающим его человеком. Функция — единица, к которой это имя прикреплено. Всё остальное в чистом коде следует из серьёзного отношения к этим двум: имя, говорящее, чем вещь является, и функция, достаточно маленькая, чтобы имя честно описывало её целиком. Когда функцию трудно назвать, это обычно сообщение, что она делает больше одной вещи.

## Почему это важно

Большая часть времени на изменение уходит на понимание текущего поведения, и плохие имена прямо раздувают эту стоимость. Переменная `data` или `temp` заставляет читателя проследить, откуда она пришла и что в ней лежит. Функция `process` заставляет прочесть всё тело, чтобы узнать, проверяет она, преобразует или сохраняет. Переименование — самый дешёвый рефакторинг из существующих: оно не может ничего сломать, если инструменты не врут, и окупается при каждом последующем чтении.

## Ключевые идеи

### Имя должно говорить что, а не как

Предпочитайте имя, называющее смысл значения, тому, что описывает его тип или происхождение. `elapsedSeconds` лучше `t`, `activeSubscriptions` лучше `list`. Длина — не враг: длинное точное имя всегда лучше короткого загадочного, а обычное соглашение, по которому булевы значения читаются как вопрос или предикат, превращает условия в предложения.

```ts
// непонятно
const d = users.filter((u) => u.a === 1);

// говорит о замысле
const activeUsers = users.filter((user) => user.status === "active");
```

### Функция должна делать одну вещь

Проверка в том, можете ли вы описать её одним предложением без «и». Если предложению нужно «и», внутри две функции. Речь не о количестве строк ради него самого: у маленькой функции мало движущихся частей, поэтому читатель держит в голове всю её разом, а имя сообщает остальное.

```ts
function invoiceTotal(lines) {
  const subtotal = sumLines(lines);
  const tax = computeTax(subtotal);
  return subtotal + tax;
}
```

### Опускайте детали вниз, держите верхний уровень читаемым

Функция-координатор должна читаться как сводка. Каждая строка — один шаг того же уровня, а низкоуровневые детали — работа со строками, битовые флаги, неудобный API — живут на вызов глубже. Именно это делает файл обозримым: читатель может остановиться на нужном уровне, вместо того чтобы продираться сквозь детали, пока ему не нужные.

```ts
function importCsv(path) {
  const rows = readRows(path);
  const records = rows.map(parseRecord).filter(Boolean);
  return saveRecords(records);
}
```

### Держите число параметров небольшим

Каждый параметр — ещё одна вещь, которую вызывающий должен угадать правильно, а длинный список параметров обычно означает, что функции нужен ещё не названный замысел. Два-три удобны; дальше ищите значение, естественно группирующее остальные, или разделяйте функцию по настоящей границе. Булевы параметры — особый случай: они намекают, что за одним именем прячутся два поведения, поэтому им часто лучше стать двумя функциями.

```ts
// два поведения за одним флагом
render(record, true);

// по одному поведению каждое
renderSummary(record);
renderDetail(record);
```

### Комментарии объясняют почему, а не что

Код уже говорит, что он делает. Комментарий заслуживает места, когда записывает то, чего код не может: внешнее ограничение, обходной путь с причиной, решение, выглядящее неверным, но намеренное. Комментарий, пересказывающий следующую строку или разошедшийся с кодом, — шум, из-за которого читатель доверяет файлу меньше.

## Практика

### Переименуйте функцию, пока место вызова не станет читаться хорошо

Выберите худше всего названную функцию в файле, который вы поддерживаете. Запишите место вызова английским предложением, затем переименовывайте функцию и её параметры, пока место вызова не станет читаться как это предложение.

Готово, когда: место вызова понятно без открытия функции, и изменение свелось к чистому переименованию без правок поведения.

### Разделите одну функцию на шаги

Возьмите функцию длиннее примерно двадцати строк и перепишите её как последовательность именованных шагов одного уровня, где каждый шаг — своя маленькая функция.

Готово, когда: исходная функция читается как сводка из трёх-четырёх вызовов, и её тесты по-прежнему проходят без изменений.

## Частые ошибки

- **Имя функции по тому, как она работает** — `stringSplitAndJoin` описывает механизм, а не назначение, поэтому вызывающему приходится её читать; исправить: назовите результат, нужный вызывающему.
- **Длинная функция, чтобы избежать «слишком многих функций»** — файл кажется опрятным, а читатель не держит в голове ничего; исправить: делите по шагам, а не по числу строк.
- **Комментарий в починку плохого имени** — имя остаётся неверным, а комментарий расходится; исправить: сначала переименуйте и комментируйте только то, чего код сказать не может.
- **Сокращения ради экономии набора** — `usrMgr` стоит читателю перевода при каждом появлении; исправить: пишите имя целиком, а набор оставьте автодополнению редактора.
- **Оставленный булев параметр** — каждое место вызова читается как головоломка, а два пути стареют по-разному; исправить: разделите на две функции с именами, говорящими, какое поведение даёт каждая.
