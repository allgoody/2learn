# Plan: Lessons Content Corpus

## Objective

Turn the 8 flat seed skill lists in `seed/` (187 one-line entries) into a structured
lesson corpus under `lessons/`: **177 entries** (170 skills + 7 areas), each with a
frontmatter contract, a fixed 6-section body skeleton, 450-950-word lessons, and a
validated prerequisite graph. Deliver the authoring spec and a zero-dependency
validator that makes "done" mechanical. **Explicitly out of scope:** the Astro site,
Tailwind, React, Pagefind — that is a separate plan, run after this one.

## Conventions

**Frontmatter — every `index.md`** (fields in this order, `key: value`, arrays inline):

(Wrapped in `---` delimiter lines at the top of the file, as usual for YAML frontmatter.)

```yaml
title: React
type: skill
topic: frontend
tier: large
status: drafted
aliases: []
prereqs: ["frontend/javascript", "frontend/typescript"]
related: []
```

- `title` — string, verbatim from Appendix A.
- `type` — `skill` | `area`.
- `topic` — one of the 8 topic slugs; must equal the parent directory name.
- `tier` — `small` | `medium` | `large`. Areas are always `small`.
- `status` — `stub` | `drafted` | `reviewed`. Batch WPs write `drafted`. Only the
  user promotes to `reviewed`.
- `aliases` — string array, always present (may be empty).
- `prereqs` — string array of inventory ids, always present (may be empty).
- `related` — string array of inventory ids, always present (may be empty).

**Frontmatter — every child lesson** (`NN-<slug>.md`): exactly two fields, in order:

```yaml
title: Hooks and state
prereqs: ["frontend/react"]
```

**Child filenames:** `NN-<slug>.md`, `NN` is zero-padded and starts at `01`, slug is
lowercase-hyphenated. Children are ordered by filename ascending; there is no
`order:` field.

**Slug rules:** `^[a-z0-9]+(-[a-z0-9]+)*$`. Derived from the seed title by
lowercasing, dropping punctuation except `.js`/`.js`→`js`, `&`/`/`→`-`, dropping
parenthesised text except where the parenthetical is the common short name. **All 177
slugs are pre-computed in Appendix A** — never re-derive one.

**Body shapes — three, and only three:**

1. **Full lesson** (a `small` skill's `index.md`, and every child lesson) — 6 sections
   in this exact order, headings exactly:
   `## What it is` → `## Why it matters` → `## Core ideas` → `## Practice` →
   `## Common mistakes` → `## Go deeper`. Word count **450-950**.
2. **Track landing** (a `medium` or `large` skill's `index.md`) — 5 sections:
   `## What it is` → `## Why it matters` → `## In this track` →
   `## Prerequisites` → `## Go deeper`. Word count **200-400**. `## In this track` is
   an ordered list of the child lessons, each line `1. **<child title>** (\`<child id>\`) — <one line>`.
3. **Area page** (any `type: area`) — 4 sections:
   `## What it covers` → `## Why it matters` → `## Included skills` →
   `## Where to start`. Word count **120-300**.

**`## Core ideas` structure:** 3-6 `###` subheadings, each a noun phrase, each
followed by 2-4 sentences plus a short fenced example block where the topic allows.

**`## Practice` structure:** 1-2 `###` exercises; each ends with a line beginning
`Done when:` naming a concrete observable result.

**`## Common mistakes` structure:** 3-5 bullets, each formatted
`- **<mistake>** — <what goes wrong>; fix: <what to do instead>.`

**`## Go deeper` structure:** 2-5 bullets, each `- **<Title>** (\`<id>\`) — <why>`.
Ids must exist in the inventory.

**Validation command (every content WP):**

```bash
node tools/validate-content.mjs            # validate everything present; exit 1 on any error
node tools/validate-content.mjs --topic frontend
node tools/validate-content.mjs --strict   # also fail on entries not yet written (final phase only)
node tools/validate-content.mjs --write-index
```

**WP sizing (deliberate deviation):** code plans target ~50 lines per work package.
Content work packages are **batches of 6-20 files** grouped by one seed `##` section,
because the atomic unit of content is a topic section, not a function. Splitting
further would produce 150+ WPs of pure repetition. Every WP still names its exact
file list and is independently verifiable by the validator.

**Child filenames (plan-wide rule):** every phase file lists the exact `index.md` path
of each entry it creates, that entry's tier, and its child count. The *names* of the
child files are the writer's one design decision (spec §6): 2 titles for `medium`, 4
for `large`, written into the index's `## In this track` list before the children
are written. The validator enforces the count, the filename pattern, the contiguous
numbering and the index↔child id match. No phase file pre-assigns child names — that
would commit to titles without information the writer has at execution time.

**Git:** do not commit. The user commits. Do not run `git push` under any circumstance.
